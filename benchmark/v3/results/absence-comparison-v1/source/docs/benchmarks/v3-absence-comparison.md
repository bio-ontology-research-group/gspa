# Explicit absence and supply comparisons

The production metabolic-experiment stage can now compare four reaction-specific
explanations through `absence_comparison` in an experiment manifest. This adds a
computational comparison for audit item 8. It does **not** finish that item: real
auxotroph validation, controlled sequence-fragmentation evaluation, automated
cohort-wide scenario construction and independent gene-attribution accuracy
remain open.

## Meaning of the scenarios

All scenarios use the same SBML stoichiometry, biomass, maintenance, baseline
medium and explicitly listed interventions. They differ in these assumptions:

| Scenario | Focal activity | Candidate-assignment intervention | Environmental assumption |
|---|---|---|---|
| `missing_annotation` | Available at existing model bounds | Removes the proposed focal activity | Baseline medium |
| `missing_sequence` | Available without a retained sequence assignment | Leaves the unassigned activity available | Baseline medium |
| `pathway_loss` | Focal reaction disabled | No additional effect | Baseline medium |
| `external_supply` | Focal reaction disabled | No additional effect | Explicit bounded extracellular supply and declared transport |

`pathway_loss` tests loss of the focal reaction; it does not establish loss of
every reaction in a pathway. External supply can coexist with pathway loss, so
these are overlapping explanatory scenarios rather than mutually exclusive
probability classes. Existing baseline supplementation can make the two scenarios
indistinguishable. The output preserves that ambiguity.

The candidate intervention is deliberately named
`candidate_assignment_knockout`. It tests the proposed assignment only. It is
not a prediction of all effects of deleting a multifunctional biological gene.
The original gene–reaction rules do not select or influence these scenarios.

## Production input and output

Use the existing CLI with `--experiment-mode manifest` and
`--experiment-strategy fixed`. The `--experiment-manifest` supplies an independent
model, baseline and objectives as for ordinary metabolic experiments, plus:

```json
{
  "absence_comparison": {
    "reaction": "VITS",
    "candidate_function_key": "pE|EC|EC:2.3.3.3",
    "assembly": {
      "status": "COMPLETE",
      "completeness_fraction": 1.0,
      "source": "source of assembly assessment"
    },
    "function_search": {
      "status": "COMPLETE",
      "source": "source and scope of functional search"
    },
    "external_supply": {
      "exchange": "EX_vit_e",
      "uptake_limit": 2.0,
      "transport_reactions": ["T_vit"],
      "source": "source of proposed medium and transport"
    },
    "conditions": [
      {"id": "control", "mods": []},
      {"id": "withdrawal", "mods": [{"op": "close", "exchange": "EX_vit_e"}]},
      {"id": "transport_ko", "mods": [{"op": "knockout", "reactions": ["T_vit"]}]}
    ]
  }
}
```

These reaction names belong to the synthetic mechanism fixture; they are not
universal metabolite or reaction identifiers. A full reproducible manifest is
generated by `benchmark/v3/run_absence_mechanism.py`.

The workflow binds a non-null candidate key to an actual retained, measured EC
claim and a validated EC-to-model-reaction mapping. A fabricated candidate,
unrelated mapping, or non-catalytic/complex-subunit-only role is rejected. A
complex subunit alone cannot be assumed to supply the complete reaction.
Alternative mapped reactions are recorded. No model GPR is accepted as proof of
the mapping. A same-run refiner model is rejected because its topology was
selected from the annotations under examination.

Set `candidate_function_key` to `null` when there is no retained candidate;
missing annotation then remains unavailable and no candidate intervention is
invented. Set `external_supply` to `null` when supply and transport are unknown;
external supply remains unavailable rather than becoming a negative result.
Assembly status accepts `COMPLETE`, `DRAFT` or `UNKNOWN`, with a nullable
completeness fraction. Function search accepts `COMPLETE`, `INCOMPLETE` or
`UNKNOWN`. Sources are required. These are explicit user-supplied assessments:
neither completeness estimates nor whole-proteome family searches establish
functional absence. Changing these metadata does not fabricate a probability
or disable the missing-sequence hypothesis.

Transport must connect the specified external species to an internal compartment.
Other direct transport reactions for that species are closed in every scenario.
Declared alternatives remain available; removing one port need not remove an
alternative port. Supply is an exact finite total uptake cap. Interventions apply
after supply, so withdrawal closes the proposed supply. Both stoichiometric sign
conventions are supported. Explicit lower-bound requirements remain constraints:
disabling a required activity yields a contradiction rather than relaxing the
requirement and manufacturing a rescue.

The result schema is `gspa.absence_experiments/1`. It records the complete
assumptions, model hash, condition-by-scenario cells, solver ledger, unavailable
cases and unvisited conditions. Budget allocation reserves every available
scenario and candidate intervention for a condition before starting that
condition. The workflow verifies the complete comparison, candidate and medium
identity, budget, condition partition, phenotype classes and pairwise summaries.

Pairwise summaries compare growth versus failure to grow under evaluated
interventions. Infeasibility and feasible zero growth retain different solver
diagnostics, but do not become distinct observable growth phenotypes. Solver
errors remain unknown. A matching pattern means only matching evaluated growth
classes, not biological equivalence. No explanation is selected; gene attribution
stays `unverified`, probability stays null, and promotion stays `none`. No result
is inserted into learned features or changes a functional prediction.

## Validation and limits

The regressions use real SBML parsing and LP solves. They cover the four
intervention patterns, candidate and supply unavailability, complete/draft/unknown
metadata, bounded supply, withdrawal, alternative transport, reversed reaction
signs, required maintenance, solver failure, whole-condition budgets and hidden
GPR/context invariance. Production workflow tests check retained-claim binding,
mapping rejection, missing candidates, insufficient budget and tampered results.

`benchmark/v3/check_absence_cobra.py` independently reads SBML with COBRApy and
solves with GLPK. It imports neither the production parser nor the production
solver. It rebuilds each scenario on a fresh model and compares status and growth;
its tests include isolation across interventions and changed-input rejection.

`benchmark/v3/run_absence_mechanism.py` runs the actual production CLI on eight
scenario variants plus a baseline. It compares functional TSV and candidate
feature bytes to baseline and retains independent solver comparisons. Its
`fragmented` variant changes explicit assembly/candidate metadata; it does not
perform nucleotide fragmentation and is not evidence of biological accuracy.

The new explicit analysis is a single focal reaction/candidate comparison. It
does not yet generate scenarios automatically from every cohort gap, join
measured phenotype truth, model a producer community, identify a real
transporter, or estimate false enzyme-attribution rates. The existing community
stage remains separate. These limitations keep audit items 8, 9 and 12 open.

## Recorded gate results (2026-10-27)

- 1,251 JVM cases pass, with two optional skips; all four live HMMER/AntiFam
  cases execute.
- 613 benchmark cases pass, with three optional skips and ten executed live
  Nextflow cases. This includes three new independent-oracle checks.
- 89 metabolic/assignment/absence Python cases pass, including 16 new absence
  cases and the actual Python CLI.
- Nine production Java CLI runs pass. All eight experimental variants preserve
  baseline functional TSV and candidate feature bytes. All 147 available
  independent COBRApy/GLPK phenotype comparisons agree; the insufficient-budget
  case remains untested, with no solver calls or comparison credit.

The initial workflow gate exposed two test expectation errors (set versus list,
and a zero budget disallowed by workflow configuration). The first oracle gate
used a Python-3.11-only hashing API in the Python 3.10 environment; a streaming
hash implementation repaired compatibility. Failure logs are retained alongside
the passing gates. Neither failure is omitted from the evidence history.
